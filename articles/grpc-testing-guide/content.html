gRPC становится стандартом де-факто для высоконагруженного межсервисного взаимодействия в микросервисной архитектуре. Благодаря бинарному протоколу Protocol Buffers и транспорту HTTP/2, gRPC обеспечивает десятикратный прирост производительности по сравнению с традиционным REST JSON API. Однако для QA-инженера переход на gRPC влечет за собой смену привычных инструментов и подходов к тестированию: от отсутствия привычных HTTP-методов и JSON-пейлоадов в сникере трафика до специфичных статусов ошибок и 4 режимов стриминга. В этом практическом руководстве мы подробно разберем архитектуру gRPC, научимся тестировать сервисы вручную через grpcurl и Postman, настроим кодогенерацию на Python и напишем полноценный фреймворк автотестов на PyTest с мокированием и нагрузочным тестированием.

Часть 1. REST vs gRPC: В чем разница?

Чтобы эффективно тестировать gRPC, важно понять, чем он принципиально отличается от классического REST API. В REST мы привыкли оперировать ресурсами (URL), HTTP-методами (GET, POST, PUT, DELETE) и текстовым JSON-форматом. В gRPC мы вызываем удаленные функции (RPC — Remote Procedure Call) прямо как обычные методы в коде, а данные передаются в строгом бинарном формате.

Характеристика REST API gRPC API
Транспортный протокол HTTP/1.1 (текстовый) или HTTP/2 HTTP/2 (строго бинарный)
Формат данных JSON / XML (текстовый, избыточный) Protocol Buffers (компактный бинарный)
Контракт (Схема) OpenAPI (Swagger) — опционально .proto файлы — обязательно (Strict Types)
Режимы передачи Request / Response (полинговые WebSocket отдельно) Unary + 3 вида Streaming (двунаправленный)
Производительность Средняя (парсинг JSON требует CPU) Высокая (сериализация до 7-10 раз быстрее)
Кодогенерация Сторонние генераторы (Swagger Codegen) Встроена в экосистему protoc для 10+ языков

Магия Protocol Buffers и HTTP/2

Превосходство gRPC держится на двух ключевых китах:

⚡ 1. Protocol Buffers (Protobuf)

Вместо передачи названий ключей (например, "user_first_name": "Alexander") Protobuf кодирует данные под чисельными тэгами полей (field tags: 1, 2, 3). Это уменьшает размер сетевого пакета в 5–8 раз и устраняет затратный парсинг строк.

🚀 2. HTTP/2 Transport

HTTP/2 поддержит мультиплексирование (сотни параллельных запросов внутри одного TCP-соединения), сжатие заголовков (HPACK) и двунаправленный постоянный стриминг данных без постоянных лишних handshake.

4 типа взаимодействия в gRPC

При тестировании gRPC сервисов вы встретите 4 модели работы методов:

1. Unary RPC

Классический вызов: 1 запрос ➡️ 1 ответ. Аналог привычного REST.

2. Server Streaming

1 запрос ➡️ Поток ответов (например, лог событий, курсы валют в live).

3. Client Streaming

Поток запросов ➡️ 1 финальный ответ (загрузка файлов по кускам, телеметрия).

4. Bidirectional Streaming

Поток запросов 🔄 Поток ответов в реальном времени (чат, гео-трекинг).

Часть 2. Ручное и CLI тестирование gRPC

Прежде чем писать автоматизированные тесты на Python, проверим сервис вручную. В мире REST для этого используют curl или Postman. В gRPC аналогом является утилита grpcurl.

⚠️ Внимание: Reflection API
Чтобы grpcurl или GUI-клиенты могли автоматически показывать доступные методы и структуру сообщений без локального .proto файла, на gRPC-сервере должен быть включен Server Reflection Protocol. На стейджинг-серверах его включение настоятельно рекомендуется для тестировщиков!

Полезные команды grpcurl

# 1. Просмотреть список всех доступных gRPC сервисов на сервере
grpcurl -plaintext localhost:50051 list

# 2. Получить список методов конкретного сервиса
grpcurl -plaintext localhost:50051 list order.v1.OrderService

# 3. Инспекция структуры метода и тип входных/выходных Protobuf сообщений
grpcurl -plaintext localhost:50051 describe order.v1.OrderService.CreateOrder

# 4. Вызов Unary метода с передачей JSON дэйты (преобразуется в Protobuf)
grpcurl -plaintext -d '{"user_id": 101, "items": ["item_1", "item_2"]}' \
  localhost:50051 order.v1.OrderService/CreateOrder

# 5. Передача метаданных (авторизация, токены, трассировка) через заголовки
grpcurl -plaintext -H "authorization: Bearer secret_jwt_token" \
  -d '{"order_id": "ORD-9988"}' \
  localhost:50051 order.v1.OrderService/GetOrder

GUI-инструменты: Postman & Kreya

Если вы предпочитаете графический интерфейс:

  • Postman (с версий 9.0+): Поддерживает gRPC из коробки. Достаточно загрузить .proto файл или включить Server Reflection, ввести URL вида localhost:50051 и выбирать методы из выпадающего списка.
  • Kreya / BloomRPC: Специализированные клиенты для gRPC. Позволяют удобно сохранять коллекцию запросов, редактировать метаданные и тестировать все виды стриминга.

Часть 3. Настройка Python & Proto схемы

Для автоматизации gRPC тестов на Python нам понадобятся официальные библиотеки Google gRPC и тестовый фреймворк PyTest.

Установка зависимостей

pip install grpcio grpcio-tools pytest pytest-asyncio

Проектирование схемы order_service.proto

Создадим тестовый контракт микросервиса заказов protos/order_service.proto:

syntax = "proto3";

package order.v1;

service OrderService {
  // Unary RPC: Создание заказа
  rpc CreateOrder (CreateOrderRequest) returns (CreateOrderResponse);

  // Unary RPC: Получение заказа по ID
  rpc GetOrder (GetOrderRequest) returns (Order);

  // Server Streaming RPC: Получение истории статусов заказа в реальном времени
  rpc TrackOrderStatus (TrackOrderRequest) returns (stream OrderStatusUpdate);

  // Client Streaming RPC: Пакетная загрузка товаров в заказ
  rpc UploadOrderItems (stream UploadItemRequest) returns (UploadItemSummary);
}

message CreateOrderRequest {
  int64 user_id = 1;
  repeated string item_ids = 2;
  double total_amount = 3;
}

message CreateOrderResponse {
  string order_id = 1;
  string status = 2;
  string created_at = 3;
}

message GetOrderRequest {
  string order_id = 1;
}

message Order {
  string order_id = 1;
  int64 user_id = 2;
  repeated string item_ids = 3;
  double total_amount = 4;
  string status = 5;
}

message TrackOrderRequest {
  string order_id = 1;
}

message OrderStatusUpdate {
  string order_id = 1;
  string status = 2;
  int64 timestamp = 3;
}

message UploadItemRequest {
  string order_id = 1;
  string item_id = 2;
  int32 quantity = 3;
}

message UploadItemSummary {
  string order_id = 1;
  int32 total_items_uploaded = 2;
  bool is_success = 3;
}

Компиляция .proto схемы в Python-код

Для генерации статических модулей структуры данных и gRPC клиентских стабов выполним команду:

python -m grpc_tools.protoc \
  -I./protos \
  --python_out=./generated \
  --grpc_python_out=./generated \
  ./protos/order_service.proto

В результате в директории generated/ появятся два сгенерированных файла:

  • order_service_pb2.py — содержит Protobuf классы сообщений (CreateOrderRequest, Order и т.д.).
  • order_service_pb2_grpc.py — содержит клиентские стабы (OrderServiceStub) и серверные интерфейсы.

Часть 4. Автоматизация на PyTest

Автотесты для Unary RPC

Напишем автотесты для одиночных (Unary) вызовов CreateOrder и GetOrder в файле test_order_service.py:

import pytest
import grpc
import order_service_pb2 as pb2

class TestCreateOrder:

    def test_create_order_success(self, order_stub, auth_metadata):
        """
        Позитивный тест: Успешное создание заказа со всеми валидными полями.
        """
        request = pb2.CreateOrderRequest(
            user_id=4042,
            item_ids=["phone-apple-15", "case-silicone"],
            total_amount=1200.50
        )

        # Вызов Unary RPC с передачей metadata и timeout (в секундах)
        response = order_stub.CreateOrder(request, metadata=auth_metadata, timeout=5.0)

        # Валидация ответа от gRPC сервиса
        assert response.order_id != "", "Order ID не должен быть пустым"
        assert response.status == "CREATED", f"Неожиданный статус: {response.status}"
        assert len(response.order_id) > 5

    def test_create_order_invalid_amount(self, order_stub, auth_metadata):
        """
        Негативный тест: Попытка создать заказ с отрицательной суммой.
        Ожидаем статус ошибки INVALID_ARGUMENT (4).
        """
        request = pb2.CreateOrderRequest(
            user_id=4042,
            item_ids=["item-1"],
            total_amount=-50.0
        )

        # Проверяем, что сервер генерирует grpc.RpcError
        with pytest.raises(grpc.RpcError) as exc_info:
            order_stub.CreateOrder(request, metadata=auth_metadata, timeout=3.0)

        # Валидация gRPC кода ошибки и сообщения
        err = exc_info.value
        assert err.code() == grpc.StatusCode.INVALID_ARGUMENT
        assert "Total amount cannot be negative" in err.details()

Автотесты для Streaming RPC

Тестирование стриминга — уникальная фича gRPC. Разберем, как тестировать Server Streaming и Client Streaming в PyTest.

class TestOrderStreaming:

    def test_server_streaming_track_order_status(self, order_stub, auth_metadata):
        """
        Тестирование Server Streaming RPC:
        Сервер возвращает итератор ответов в реальном времени.
        """
        request = pb2.TrackOrderRequest(order_id="ORD-1002")

        # В Server Streaming вызов возвращает генератор/итератор
        response_stream = order_stub.TrackOrderStatus(request, metadata=auth_metadata, timeout=10.0)

        collected_statuses = []
        for status_update in response_stream:
            collected_statuses.append(status_update.status)

        # Проверяем последовательность смены статусов заказа
        expected_workflow = ["PROCESSING", "SHIPPED", "DELIVERED"]
        assert collected_statuses == expected_workflow, f"Неверный порядок статусов: {collected_statuses}"

    def test_client_streaming_upload_items(self, order_stub, auth_metadata):
        """
        Тестирование Client Streaming RPC:
        Клиент передает итератор/генератор сообщений серверу.
        """
        def generate_items():
            items = [
                pb2.UploadItemRequest(order_id="ORD-5500", item_id="item-A", quantity=2),
                pb2.UploadItemRequest(order_id="ORD-5500", item_id="item-B", quantity=1),
                pb2.UploadItemRequest(order_id="ORD-5500", item_id="item-C", quantity=5),
            ]
            for item in items:
                yield item

        # Передаем функцию-генератор в качестве единственного аргумента
        response = order_stub.UploadOrderItems(generate_items(), metadata=auth_metadata, timeout=5.0)

        assert response.is_success is True
        assert response.total_items_uploaded == 3
        assert response.order_id == "ORD-5500"

Проверка gRPC Status Codes

В отличие от HTTP, где используются статус-коды 200, 400, 404, 500, в gRPC определены 16 канонических статусов ошибки (gRPC Status Codes). В таблице ниже приведены главные коды, которые QA обязан уметь проверять в автотестах:

Code Название статуса HTTP аналог Когда возникает в QA тестах
0 OK 200 OK Запрос успешно обработан.
3 INVALID_ARGUMENT 400 Bad Request Ошибка валидации полей (негативный баланс, пустой ID).
4 DEADLINE_EXCEEDED 504 Gateway Timeout Истек таймаут выполнения запроса (timeout=N).
5 NOT_FOUND 404 Not Found Запрошенный ресурс/заказ не существует в базе.
16 UNAUTHENTICATED 401 Unauthorized Отсутствует или невалиден JWT-токен в Metadata.
7 PERMISSION_DENIED 403 Forbidden У пользователя нет прав на выполнение операции.

Часть 5. Мокирование gRPC сервиса на Python

При микросервисной архитектуре тестируемый сервис часто зависит от внешних gRPC-сервисов (например, Billing Service или Inventory Service). Чтобы сделать автотесты независимыми от внешнего окружения, мы поднимаем локальный Mock gRPC Server прямо в тестах PyTest.

Пример реализации Mock-сервера на Python

import pytest
import grpc
from concurrent import futures
import order_service_pb2 as pb2
import order_service_pb2_grpc as pb2_grpc

# 1. Создаем тестовую фейковую реализацию сервиса
class MockOrderServicer(pb2_grpc.OrderServiceServicer):

    def CreateOrder(self, request, context):
        if request.user_id == 999:
            context.abort(grpc.StatusCode.PERMISSION_DENIED, "User is blacklisted")
        return pb2.CreateOrderResponse(
            order_id="MOCK-ORDER-777",
            status="CREATED",
            created_at="2026-08-02T12:00:00Z"
        )

@pytest.fixture(scope="module")
def mock_grpc_server():
    """
    Фикстура, запускающая в фоновом потоке тестовый gRPC сервер на порту 50052.
    """
    server = grpc.server(futures.ThreadPoolExecutor(max_workers=2))
    pb2_grpc.add_OrderServiceServicer_to_server(MockOrderServicer(), server)
    server.add_insecure_port("127.0.0.1:50052")
    server.start()
    yield "127.0.0.1:50052"
    server.stop(grace=None)

def test_mocked_create_order(mock_grpc_server):
    # Подключаемся к нашему Mock-серверу
    with grpc.insecure_channel(mock_grpc_server) as channel:
        stub = pb2_grpc.OrderServiceStub(channel)
        
        request = pb2.CreateOrderRequest(user_id=101, item_ids=["item-1"], total_amount=100.0)
        response = stub.CreateOrder(request)
        
        assert response.order_id == "MOCK-ORDER-777"
        assert response.status == "CREATED"

Часть 6. Нагрузочное тестирование gRPC с ghz

Классический Apache JMeter или Locust не всегда оптимальны для gRPC из-за специфики бинарного транспорта HTTP/2. Каноническим и самым мощным CLI-инструментом для нагрузочного тестирования gRPC является утилита ghz (написана на Go).

Пример запуска нагрузки через ghz

# Запуск 10,000 запросов с параллельностью 50 виртуальных пользователей
ghz --insecure \
  --proto=./protos/order_service.proto \
  --call=order.v1.OrderService.CreateOrder \
  --data='{"user_id": 101, "item_ids": ["item_1"], "total_amount": 199.99}' \
  --metadata='{"authorization":"Bearer test_token"}' \
  -c 50 \
  -n 10000 \
  --timeout=2s \
  localhost:50051

Утилита ghz генерирует подробный консольный отчет и гистограмму задержек (Latency distribution: p50, p95, p99), а также измеряет общее количество успешных запросов в секунду (RPS).

Часть 7. Матрица Тест-кейсов & QA Чек-лист

Чтобы ничего не упустить при подготовке тестового покрытия gRPC сервисов, используйте готовую проверенную матрицу тест-кейсов:

Категория Что проверяем (Тест-кейс) Ожидаемый результат
Контракты (Schema) Совместимость .proto файлов, отсутствие breaking changes при изменении полей. Старые клиенты не падают при добавлении новых полей в Protobuf.
Валидация типов Передача граничных значений типов (int32 max, float, null/default значения). Возврат INVALID_ARGUMENT (3) с подробным описанием ошибки.
Метаданные & Auth Отправка запросов без JWT токена или с просроченным токеном в Metadata. Возврат UNAUTHENTICATED (16).
Таймауты & Deadlines Имитация медленного ответа сервера при timeout=1.0s. Клиент завершает запрос с DEADLINE_EXCEEDED (4).
Стриминг (Streaming) Обрыв сетевого соединения посередине передачи поток данных. Сервер и клиент корректно освобождают ресурсы без утечек памяти.
Размер сообщений Отправка пейлоада превышающего дефолтный лимит gRPC (обычно 4MB). Возврат RESOURCE_EXHAUSTED (8).
