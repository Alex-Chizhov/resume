В современной IT-индустрии знание ОС Linux стало фундаментальным требованием для QA-инженера и SDET любого уровня. Тестовые стенды, микросервисы, Docker-контейнеры, CI/CD пайплайны (GitLab CI, GitHub Actions) и нагрузочные генераторы работают на базе Linux. Способность быстро подключиться к серверу по SSH, локализовать баг в логах бэкенда, проверить сетевые сокеты или протестировать REST API прямо из терминала выделяет сильного специалиста. В этом исчерпывающем руководстве мы разберем более 50 ключевых CLI-команд по группам задач, изучим продвинутый анализ логов (grep, journalctl, jq, zgrep) и разберем реальные сценарии локализации дефектов.

Часть 1. Введение: Зачем QA-инженеру знание Linux

При тестировании веб-приложений и микросервисов эпоха простых графических интерфейсов ушла в прошлое. Современный QA-инженер регулярно сталкивается с задачами, требующими прямого взаимодействия с серверной ОС:

  • Локализация дефектов: Если при нажатии кнопки на фронтенде появляется ошибка «500 Internal Server Error», ответ кроется не в браузерном DevTools, а в логах серверных приложений на Linux.
  • Управление тестовыми стендами: Перезапуск упавших сервисов через systemctl, проверка статуса контейнеров Docker, просмотр переменных окружения.
  • Проверка интеграций и сетей: Эмуляция вызовов API с помощью curl, проверка доступности микросервисов через ping, nc или ss.
  • Работа в CI/CD: Написание и отладка bash-скриптов для автотестов в GitHub Actions / GitLab CI agents, создающих и очищающих окружение.

Иерархия каталогов Linux (FHS): Что нужно знать QA

В отличие от Windows с дисками C:\ и D:\, в Linux существует единое дерево файловой системы, начинающееся с корневого каталога / (Root):

Каталог Назначение и ценность для QA
/var/log/ Главное место хранения логов системных служб, Nginx, PostgreSQL, приложений.
/etc/ Конфигурационные файлы системы и сервисов (например, `/etc/nginx/nginx.conf`, `/etc/hosts`).
/tmp/ Временные файлы. Удобно использовать для хранения дампов артефактов тестов.
/home/user/ Домашние директории пользователей. Здесь обычно размещаются репозитории с автотестами.
/proc/ & /sys/ Виртуальные файловые системы, отражающие информацию о ядре, CPU и запущенных процессах.

Часть 3. Глубокое погружение в работу с логами в Linux

Логи — это главный источник истины для тестировщика. Если при автоматизации или ручном тестировании сервис ответил ошибкой `500 Internal Server Error`, грамотный QA сразу же открывает терминал Linux.

Где искать логи в Linux?

  • /var/log/syslog или /var/log/messages — системные логи ОС Linux.
  • /var/log/nginx/access.log — входящие HTTP-запросы веб-сервера.
  • /var/log/nginx/error.log — ошибки веб-сервера (проблемы с проксированием к бэкенду, 502 Bad Gateway).
  • docker logs -f CONTAINER_ID — вывод логов изолированного приложения внутри Docker.

Мониторинг логов в реальном времени (`tail -f`)

При воспроизведении дефекта на тестовом стенде запустите отслеживание логов в реальном времени с помощью tail -f. Все новые строки лога будут мгновенно появляться на вашем экране.

realtime_logging.sh 
# 1. Просмотр последних 100 строк лога приложения с авто-обновлением
tail -f -n 100 /var/log/app/backend.log

# 2. Фильтрация реального потока логов по ключевым словам ERROR или WARN
tail -f /var/log/app/backend.log | grep -E --color=always "ERROR|WARN|Exception"

Поиск по регулярным выражениям: `grep`, `egrep` и `zgrep`

Когда файл логов разрастается до сотен мегабайт, просматривать его вручную невозможно. На помощь приходит `grep` и его модификации.

grep_examples.sh 
# 1. Поиск падений с подсвечиванием совпадений и выводом 5 строк ДО и ПОСЛЕ ошибки
grep -i -C 5 "NullPointerException" /var/log/app/backend.log

# 2. Подсчет количества 500 ошибок в access.log Nginx
grep " 500 " /var/log/nginx/access.log | wc -l

# 3. Поиск в РОТИРОВАННЫХ архивных логах (.gz) без их предварительной распаковки
zgrep -i "database connection failed" /var/log/app/backend.log.*.gz

Парсинг структурированных JSON-логов через `jq`

Современные микросервисы генерируют логи в формате JSON (JSON Lines). Команда jq позволяет превратить мешанину сырого текста в удобочитаемый вид и выполнять сложные выборки.

jq_json_logging.sh 
# 1. Красивое форматирование (pretty print) JSON-логов
cat app_json.log | jq . | less

# 2. Выборка только тех записей, где уровень лога равен ERROR
cat app_json.log | jq 'select(.level=="error" or .level=="ERROR")'

# 3. Извлечение времени, статуса ответа и трассировки стека ошибки (trace_id)
cat app_json.log | jq -r 'select(.status >= 500) | [.timestamp, .status, .path, .errorMessage] | @tsv'

Анализ системных логов через `journalctl` (Systemd)

В современных Linux-дистрибутивах (Ubuntu, Debian, RHEL, CentOS) управлением сервисами занимается `systemd`, а их логи хранятся в бинарном журнале journald.

journalctl_commands.sh 
# 1. Просмотр логов конкретного сервиса (например, backend-api)
sudo journalctl -u backend-api.service -n 100 --no-pager

# 2. Просмотр логов за конкретный временной интервал
sudo journalctl -u backend-api.service --since "2026-07-31 00:00:00" --until "2026-07-31 02:00:00"

# 3. Фильтрация только ошибок уровня ERROR и CRITICAL (Priority 3)
sudo journalctl -u backend-api.service -p err -f

Часть 4. Практические сценарии QA-инженера

Сценарий 1: Локализация 500 ошибки при тестировании REST API

Представьте: автотест упал с ответом `500 Internal Server Error` на эндпоинт `/api/v1/orders`. Алгоритм действия QA в Linux:

debug_500_error.sh 
# Шаг 1. Отправляем запрос через curl для воспроизведения с выводом всех заголовков (-v)
curl -v -X POST https://staging.example.com/api/v1/orders \
  -H "Content-Type: application/json" \
  -d '{"product_id": 999, "quantity": 1}'

# Шаг 2. Подключаемся по SSH на стенд и ищем точное время падения в логе бэкенда
ssh qa@staging.example.com "grep -C 10 '/api/v1/orders' /var/log/app/orders-service.log | tail -n 30"

Сценарий 2: Поиск причины ошибки "Port 8080 already in use"

При запуске локального тестового окружения или автотестов вы видите ошибку блокировки порта.

fix_port_conflict.sh 
# 1. Находим PID процесса, прослушивающего порт 8080
sudo lsof -i :8080

# Вывод: COMMAND   PID USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
#        python3  4812   qa    3u  IPv4  42109      0t0  TCP *:8080 (LISTEN)

# 2. Завершаем зависший процесс
kill -9 4812

Сценарий 3: Передача артефактов и отчетов (SCP / Rsync)

copy_reports.sh 
# Загрузка локального Allure-отчета на веб-сервер Linux
scp -r ./allure-report qa@192.168.1.100:/var/www/html/reports/build_105

Часть 5. Ошибки новичков и чек-лист QA

⚠️ Топ-4 Типичных ошибок QA в Linux:
  • Выполнение всех команд от `root` или с `sudo`: Это может случайными действиями нарушить права доступа на файлы или повредить системные пакеты.
  • Попытка открыть гигабайтный файл лога через `nano` или `vim`: Переполняет RAM сервера и приводит к зависанию сессии. Используйте less, tail или grep.
  • Забытые фоновые процессы: Запуск автотестов без явного завершения, забивающий ресурсы сервера.
  • Удаление файлов без проверки пути: Опасность команды `rm -rf / path/to/dir` с пробелом.

📋 Чек-лист навыков Linux для QA-инженера

  • ☑️ Умение подключаться к серверу по SSH с использованием RSA/Ed25519 ключей.
  • ☑️ Свободная навигация по дискам и поиск файлов логов (`ls -la`, `find`, `du -sh`).
  • ☑️ Мониторинг откликов бэкенда в реальном времени (`tail -f`, `grep -i`).
  • ☑️ Умение распарсить JSON-лог через `jq` и найти строку с `trace_id`.
  • ☑️ Проверка статуса служб и контейнеров (`systemctl status`, `docker ps`, `docker logs`).
  • ☑️ Проверка открытых портов и отправка HTTP-запросов из консоли (`ss -tulpn`, `curl`).

Заключение

Уверенное владение командной строкой Linux поднимает экспертизу QA-инженера на новый уровень. Вы сможете не просто заводить баг-репорты вида «Кнопка не работает», а прикладывать точную трассировку стека из логов, данные о сетевых запросах и состоянии системных ресурсов сервера.
