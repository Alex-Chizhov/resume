Вопросы обеспечения безопасности и правильного разграничения прав доступа — одна из ключевых сфер ответственности QA-инженера. По данным отчетов OWASP API Security Top 10, уязвимости типа BOLA (Broken Object Level Authorization / IDOR) и BFLA (Broken Function Level Authorization) из года в год занимают первые строчки среди самых критических брешей в современных веб-приложениях и микросервисах. В этом масштабном практическом руководстве мы подробнейшим образом разберем разницу между аутентификацией и авторизацией, изучим ключевые протоколы (Basic Auth, JWT Bearer, Cookie/Session, API Keys, OAuth 2.0 / OIDC), сравним модели контроля доступа (RBAC, ABAC, ReBAC) и построим полноценный фреймворк автотестирования на Python и PyTest с детальной матрицей тест-кейсов.

Часть 1. AuthN vs AuthZ: В чем принципиальная разница?

В инженерной среде термины Authentication и Authorization часто ошибочно объединяют, однако в QA и информационной безопасности они обозначают два абсолютно разных этапа проверки запроса.

🔑 Аутентификация (AuthN)

Вопрос: «Кто вы такой?»

Процесс проверки подлинности субъекта (пользователя или сервиса) на основе предоставленных учётных данных (пароль, токен, сертификат, биометрия).

  • Проверка логина и пароля
  • Валидация подписи JWT-токена
  • Проверка OTP-кода из 2FA

🛡️ Авторизация (AuthZ)

Вопрос: «Что вам разрешено делать?»

Процесс проверки прав аутентифицированного субъекта на выполнение конкретной операции над конкретным ресурсом.

  • Может ли Manager удалить этот отчет?
  • Доступен ли клиентский профиль N пользователю X?
  • Проверка привилегий RBAC / ABAC

Анатомия HTTP: 401 Unauthorized vs 403 Forbidden

Строгое понимание HTTP-статусов критично при составлении баг-репортов и написании проверок в автотестах. Самая распространенная путаница возникает между кодами 401 и 403.

Код ответа Название RFC Причина возникновения Заголовки и особенности
401 Unauthorized Unauthenticated Запрос не содержит валидных учётных данных (токен отсутствует, истёк, искажен или неверные логин/пароль). Сервер может вернуть заголовок WWW-Authenticate с предложением схемы аутентификации.
403 Forbidden Unauthorized / Forbidden Сервер узнал пользователя (аутентификация успешна), но у него нет прав на данный ресурс или действие. Повторная отсылка тех же учётных данных не поможет — требуется смена роли или выдача прав.
429 Too Many Requests Rate Limited Превышен лимит запросов для API-ключа, IP-адреса или токена пользователей (защита от Brute Force). Содержит заголовок Retry-After с указанием времени ожидания в секундах.
⚠️ Нюанс информационной безопасности: В некоторых критичных системах (например, финтех или банкинг) при попытке обратиться к чужому ресурсу (IDOR) вместо 403 Forbidden специально возвращается 404 Not Found. Это делается для того, чтобы злоумышленник не смог подтвердить факт существования объекта с конкретным ID в системе (защита от сканирования IDs).

Часть 2. Виды авторизации и аутентификации

1. Basic Authentication & API Keys

Basic Auth — один из самых старых механизмов HTTP-аутентификации. Клиент отправляет заголовок Authorization, в котором передаются имя пользователя и пароль, объединенные двоеточием и закодированные в Base64.

HTTP Basic Auth Header Example 
GET /api/v1/user/profile HTTP/1.1
Host: api.qalify.ru
Authorization: Basic YWxleDpzZWNyZXQwMDc=

Значение YWxleDpzZWNyZXQwMDc= легко декодируется обратно в alex:secret007. Именно поэтому Basic Auth допускается к использованию исключительно по защищенному протоколу HTTPS.

API Keys (API-ключи) представляет собой уникальную секретную строку (например, qf_live_8f7b9c1d2e3f4a5b6c7d8e9f), выдаваемую разработчику. Ключ передается либо в кастомном заголовке (X-API-Key, X-Auth-Token), либо в качестве query-параметра URL (что менее безопасно из-за логирования в nginx/HAProxy).

2. Bearer Tokens & JWT (JSON Web Tokens)

В современной микросервисной архитектуре стандартом де-факто стал Bearer Token (RFC 6750), обычно реализованный в виде **JWT (RFC 7519)**. Токен передается в заголовке Authorization: Bearer <TOKEN>.

JWT состоит из трех частей, разделенных точками (Header.Payload.Signature):

  • Header (Заголовок): Содержит тип токена и алгоритм подписи (например, {"alg": "RS256", "typ": "JWT"}).
  • Payload (Полезная нагрузка / Claims): Данные о пользователе, его ролях, времени выдачи (iat) и времени тухания (exp).
  • Signature (Цифровая подпись): Создается путем хеширования Header + Payload секретным ключом сервера (HMAC) или закрытым ключом (RSA/ECDSA).

🔄 Access vs Refresh Tokens Flow:

  1. Access Token: Живет коротко (5–15 минут), передается в каждом API-запросе, проверяется микросервисами автономно без обращения к БД.
  2. Refresh Token: Живет долго (7–30 дней), хранится в защищенном хранилище (HttpOnly Cookie), используется только для получения новой пары токенов на эндпоинте /auth/refresh.

3. Cookie & Session-based Auth + CSRF

Традиционный подход для монолитных веб-приложений (Django, Ruby on Rails, Laravel, Spring MVC):

  1. Пользователь отправляет формы логина.
  2. Сервер создает сессию в памяти/Redis и отправляет клиенту заголовок Set-Cookie: sessionid=xyz123; HttpOnly; Secure; SameSite=Strict.
  3. Браузер автоматически прикрепляет эту Cookie к каждому последующему запросу на этот же домен.
🛡️ Опасность CSRF (Cross-Site Request Forgery): Так как браузер автоматически подставляет Cookie к запросам, злоумышленник может заставить пользователя перейти на вредоносный сайт, который незаметно отправит POST /account/transfer. Для защиты используются **CSRF-токены** (Header X-CSRF-Token) и атрибут куки SameSite=Strict/Lax.

4. OAuth 2.0 & OpenID Connect (OIDC)

OAuth 2.0 — это протокол авторизации (выдача прав стороннему приложению без передачи ему логина и пароля, например «Войти через Google/GitHub»). OpenID Connect (OIDC) — это тонкая надстройка поверх OAuth 2.0 для аутентификации, добавляющая токен идентификации (ID Token в формате JWT) и эндпоинт /userinfo.

Главные типы Authorization Grants в OAuth 2.0:
  • Authorization Code Grant + PKCE (Proof Key for Code Exchange): Стандарт для Single Page Applications (React/Vue/Angular) и мобильных приложений. Защищает от перехвата авторизационного кода.
  • Client Credentials Grant: Для коммуникации между серверами (Machine-to-Machine / Service-to-Service).
  • Resource Owner Password Credentials (Legacy): Передача логина/пароля напрямую в OAuth-сервер (устарел, не рекомендуется RFC).

Часть 3. Модели управления доступом

Когда система проверила подлинность пользователя, в дело вступает движок проверки правил доступа (Access Control Engine). Существуют три основные архитектурные модели:

Модель Принцип работы Пример бизнес-логики Плюсы и минусы
RBAC
Role-Based		 Права привязываются к ролям (Admin, Manager, Editor, User). Пользователям назначаются роли. Только пользователь с ролью FinanceManager может генерировать финансовые отчеты. 🟢 Просто настроить.
🔴 Взрывное разрастание ролей (Role Explosion).
ABAC
Attribute-Based		 Доступ рассчитывается динамически на основе атрибутов субъекта, ресурса, действия и контекста окружения. Врач из Департамента А может смотреть карту пациента в рабочее время (09:00-18:00) с корпоративного IP. 🟢 Невероятная гибкость.
🔴 Сложность отладки и тестирования.
ReBAC
Relationship-Based		 Доступ определяется связями в графе объектов (Google Zanzibar model). Пользователь может редактировать документ, если он является Viewer в Папке, содержащей данный документ. 🟢 Идеально для Google Docs/Figma.
🔴 Требует специализированных движков (SpiceDB).

Уязвимости BOLA/IDOR и BFLA: Главный фокус QA

При тестировании авторизации ручной или автоматизированный QA должен проверять не только happy path, но и специфические уязвимости разграничения прав:

  • BOLA / IDOR (Broken Object Level Authorization): Пользователь UserA с ID 101 подменяет в URL/Payload ID объекта на 102 (принадлежащий UserB) и получает доступ к чужим персональным данным.
  • BFLA (Broken Function Level Authorization): Обычный пользователь меняет HTTP-метод с GET /api/v1/users на POST /api/v1/admin/users/delete и успешно выполняет административную функцию.
  • Horizontal Privilege Escalation (Горизонтальное повышение прав): Доступ к объектам соседнего пользователя того же уровня.
  • Vertical Privilege Escalation (Вертикальное повышение прав): Обычный пользователь выполняет действия администратора системы.

Часть 4. Автоматизация на Python & PyTest

Для создания чистого, масштабируемого фреймворка тестирования авторизации построим архитектуру фикстур в conftest.py с использованием библиотеки httpx (или requests).

conftest.py 
import pytest
import httpx
import jwt
import time

BASE_URL = "https://api.qalify.ru"
JWT_SECRET = "super-secret-key-for-tests-2026"

@pytest.fixture(scope="session")
def api_client():
    """Базовый HTTP-клиент с настройкой таймаутов."""
    with httpx.Client(base_url=BASE_URL, timeout=10.0) as client:
        yield client

def generate_test_jwt(user_id: int, role: str, exp_seconds: int = 3600, secret: str = JWT_SECRET) -> str:
    """Вспомогательный генератор токенов для негативного и позитивного тестирования."""
    payload = {
        "sub": str(user_id),
        "role": role,
        "iat": int(time.time()),
        "exp": int(time.time()) + exp_seconds
    }
    return jwt.encode(payload, secret, algorithm="HS256")

@pytest.fixture
def admin_headers():
    """Фикстура с валидным JWT-токеном Администратора."""
    token = generate_test_jwt(user_id=1, role="admin")
    return {"Authorization": f"Bearer {token}"}

@pytest.fixture
def user_a_headers():
    """Фикстура обычного пользователя A (ID: 101)."""
    token = generate_test_jwt(user_id=101, role="user")
    return {"Authorization": f"Bearer {token}"}

@pytest.fixture
def user_b_headers():
    """Фикстура обычного пользователя B (ID: 102)."""
    token = generate_test_jwt(user_id=102, role="user")
    return {"Authorization": f"Bearer {token}"}

10. Примеры автотестов: Basic Auth, JWT и API Keys

test_auth_mechanisms.py 
import pytest
import httpx
import time
from conftest import generate_test_jwt, JWT_SECRET

class TestBasicAndApiKeyAuth:
    """Тестирование Basic Auth и API-ключей."""

    def test_basic_auth_success(self, api_client):
        # Позитивный тест: правильные логин и пароль
        response = api_client.get("/api/v1/basic-protected", auth=("alex", "secret007"))
        assert response.status_code == 200
        assert response.json()["authenticated"] is True

    def test_basic_auth_invalid_credentials(self, api_client):
        # Негативный тест: неверный пароль -> 401
        response = api_client.get("/api/v1/basic-protected", auth=("alex", "wrong_password"))
        assert response.status_code == 401
        assert "WWW-Authenticate" in response.headers

    def test_api_key_header_success(self, api_client):
        # Валидный API key в заголовке X-API-Key
        headers = {"X-API-Key": "qf_test_key_998877"}
        response = api_client.get("/api/v1/partner/data", headers=headers)
        assert response.status_code == 200

    def test_api_key_missing_or_invalid(self, api_client):
        # Отсутствующий API key -> 401
        response = api_client.get("/api/v1/partner/data")
        assert response.status_code == 401


class TestJwtBearerAuth:
    """Глубокие проверки безопасности JWT-токенов."""

    def test_jwt_expired_token(self, api_client):
        # 1. Проверка истекшего токена (exp в прошлом) -> 401
        expired_token = generate_test_jwt(user_id=101, role="user", exp_seconds=-3600)
        headers = {"Authorization": f"Bearer {expired_token}"}
        
        response = api_client.get("/api/v1/user/profile", headers=headers)
        assert response.status_code == 401
        assert "expired" in response.json()["detail"].lower()

    def test_jwt_invalid_signature_tampering(self, api_client):
        # 2. Проверка подделки цифровой подписи (неверный секретный ключ) -> 401
        fake_token = generate_test_jwt(user_id=101, role="user", secret="hacker-secret-key")
        headers = {"Authorization": f"Bearer {fake_token}"}
        
        response = api_client.get("/api/v1/user/profile", headers=headers)
        assert response.status_code == 401
        assert "invalid signature" in response.json()["detail"].lower()

    def test_jwt_alg_none_attack(self, api_client):
        # 3. Проверка уязвимости "alg: none" (попытка обойти подпись)
        payload = {"sub": "101", "role": "admin", "iat": int(time.time()), "exp": int(time.time()) + 3600}
        # Формируем незащищенный токен без подписи
        unsigned_token = jwt.encode(payload, key="", algorithm=None)
        headers = {"Authorization": f"Bearer {unsigned_token}"}
        
        response = api_client.get("/api/v1/admin/dashboard", headers=headers)
        # Сервер ОБЯЗАН отклонить алгоритм none
        assert response.status_code in (401, 403)

import pytest

class TestAccessControlRBAC:
    """Матричные проверки ролевой модели (RBAC)."""

    @pytest.mark.parametrize("headers, expected_status", [
        (pytest.lazy_fixture("admin_headers"), 200),     # Admin доступ разрешен
        (pytest.lazy_fixture("user_a_headers"), 403),    # User A -> 403 Forbidden
        ({}, 401),                                      # Аноним -> 401 Unauthorized
    ])
    def test_admin_delete_user_endpoint(self, api_client, headers, expected_status):
        """Проверка BFLA: Только Администратор может вызывать DELETE /api/v1/users/99."""
        response = api_client.delete("/api/v1/users/99", headers=headers)
        assert response.status_code == expected_status


class TestIdorBolaVulnerabilities:
    """Проверка уязвимостей разграничения объектов (BOLA / IDOR)."""

    def test_user_a_cannot_access_user_b_order(self, api_client, user_a_headers, user_b_headers):
        """
        User A (ID 101) пытается прочитать заказ #555, принадлежащий User B (ID 102).
        """
        order_id_belonging_to_user_b = 555

        # 1. Подтверждаем, что User B успешно получает свой заказ
        resp_b = api_client.get(f"/api/v1/orders/{order_id_belonging_to_user_b}", headers=user_b_headers)
        assert resp_b.status_code == 200

        # 2. АТАКА IDOR: User A запрашивает чужой заказ с валидным токеном User A
        resp_a = api_client.get(f"/api/v1/orders/{order_id_belonging_to_user_b}", headers=user_a_headers)
        
        # БЭКЕНД ДОЛЖЕН ВЕРНУТЬ 403 Forbidden ИЛИ 404 Not Found!
        assert resp_a.status_code in (403, 404), (
          f"Уязвимость IDOR! User A получил доступ к чужому заказу {order_id_belonging_to_user_b}. "
          f"Status Code: {resp_a.status_code}"
        )

13. Чек-лист безопасности для QA в 2026 году

✅ Финальный чек-лист автоматизатора:

  • [ ] Проверены все варианты HTTP-статусов: 401 при отсутствии/невалидности токена и 403 при недостатке ролей/прав.
  • [ ] Для JWT протестированы кейсы с истекшим exp, неверным секретом и поддельной полезной нагрузкой.
  • [ ] Настроены автотесты на BOLA/IDOR для всех эндпоинтов, принимающих `id` ресурсов в URL и body.
  • [ ] Все сессионные куки имеют флаги HttpOnly, Secure, SameSite=Strict/Lax.
  • [ ] Для внешних интеграций на базе API-ключей протестирован Rate Limiting (ответ 429).
