Контейнеризация с помощью Docker — один из самых востребованных навыков современного QA-инженера и SDET. Забудьте о бесконечных проблемах формата «у меня всё работает локально, а на CI падают тесты» или многочасовых развертываниях тестовой базы данных перед каждым прогоном. В этом практическом руководстве мы с нуля разработаем REST API сервис на FastAPI, напишем для него набор автотестов на PyTest с Allure-отчетами, упакуем всё в Docker Compose и построим полностью автоматизированный CI/CD пайплайн в GitLab CI.

Часть 1. Что такое Docker и зачем он QA-инженеру

Представьте классическую ситуацию: разработчик передает задачу на тестирование. Вы разворачиваете приложение локально, но оно отказывается запускаться. Выясняется, что у вас установлена другая версия Python, не хватает системных библиотек C++, отсутствует локальный Redis, а переменные окружения прописаны не в том формате.

Docker — это платформа автоматизации развертывания и управления приложениями в среде контейнеризации. Он позволяет запаковать приложение со всеми его зависимостями (библиотеками, переменными окружения, драйверами и конфигурациями) в единый изолированный модуль — контейнер.

💡 Зачем Docker инженеру по тестированию (QA / SDET):
  • Изоляция и воспроизводимость: Окружение на вашей локальной машине, удаленном сервере и в CI/CD пайплайне на 100% идентично.
  • Запуск в 1 клик: Поднятие сложного стека (Backend API + Postgres + Redis + Selenoid + WireMock) одной командой docker compose up.
  • Параллельный прогон: Возможность запускать несколько изолированных экземпляров тестов и сервисов одновременно на разных портах.
  • Отсутствие мусора: После прогона тестов контейнеры и их временно созданные данные удаляются без остатка в системе.

Сравнение: Виртуальные машины vs Docker Контейнеры

Частый вопрос новичков: «Чем Docker отличается от VirtualBox или VMware?». Главное отличие — на каком уровне происходит виртуализация.

Характеристика Виртуальная машина (ВМ) Docker Контейнер
Гостевая ОС Требует полноценную ОС (несколько ГБ) Использует ядро хостовой ОС (несколько МБ)
Скорость старта Минуты (долгая загрузка ОС) Милисекунды / Секунды
Потребление ресурсов Высокое (заранее выделенные RAM и CPU) Минимальное (выделение по требованию)
Производительность Снижена из-за гипервизора Нативная скорость выполнения кода

Ключевая терминология Docker

  • Image (Образ): Неизменяемый шаблон («чертеж» или слепок), содержащий код приложения, виртуальную файловую систему и зависимости. Аналог установочного диска ISO или инсталлятора.
  • Container (Контейнер): Запущенный экземпляр образа. Работающий процесс в изолированном пространстве имён. Из одного образа можно запустить 10 одинаковых контейнеров.
  • Dockerfile: Текстовый файл с последовательными инструкциями по сборке Docker-образа (какую базовую ОС взять, какие зависимости установить, какой файл запустить).
  • Docker Registry: Хранилище и реестр Docker-образов (например, открытый Docker Hub или приватный GitLab Container Registry).
  • Volume (Том): Специальный механизм для сохранения данных вне файловой системы контейнера (чтобы отчеты Allure или данные из PostgreSQL не пропали после остановки контейнера).
  • Network (Сеть): Изолированная виртуальная сеть, связывающая контейнеры между собой по имени сервиса без необходимости пробрасывать порты на хост.

Часть 2. Установка Docker и Первая Настройка

1. Windows (Docker Desktop + WSL 2)

Для работы Docker на Windows требуется подсистема Linux (WSL 2):

  1. Откройте PowerShell от имени Администратора и выполните установку WSL 2:
    powershell.exe 
    wsl --install
  2. Скачайте инсталлятор Docker Desktop for Windows.
  3. В ходе установки обязательно поставьте галочку «Use WSL 2 instead of Hyper-V».
  4. После перезагрузки ПК запустите Docker Desktop и дождитесь статуса Engine Running.

2. macOS (Apple Silicon M1/M2/M3 & Intel)

Скачайте Docker Desktop для соответствующей архитектуры (Apple Chip или Intel Chip) с официального сайта или установите через Homebrew:

terminal.app 
brew install --cask docker

3. Linux (Ubuntu / Debian)

На Linux рекомендуется устанавливать легкий docker-engine и docker-compose-plugin через официальный репозиторий:

bash 
# Обновляем индекс пакетов и устанавливаем утилиты
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg

# Добавляем официальный GPG-ключ Docker
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg

# Устанавливаем Docker Engine и Compose plugin
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# Добавляем текущего пользователя в группу docker (чтобы не писать sudo)
sudo usermod -aG docker $USER

Часть 3. Создаем Микросервис на FastAPI (3 Эндпоинта)

Для создания реалистичного тестового окружения напишем простой REST API сервис на фреймворке FastAPI. Сервис будет выполнять роль тестируемой системы (SUT — System Under Test).

Наш сервис будет содержать 3 классических эндпоинта:

  1. GET /health — Проверка доступности (Healthcheck). Возвращает status 200 OK.
  2. POST /api/v1/users — Создание нового пользователя с валидацией Pydantic. Возвращает 201 Created.
  3. GET /api/v1/users/{user_id} — Получение профиля пользователя по ID. Возвращает 200 OK или 404 Not Found.

Создадим структуру файлов нашего проекта:

Структура проекта 
qa-docker-demo/
├── app/
│   ├── __init__.py
│   └── main.py              # Исходный код FastAPI микросервиса
├── tests/
│   ├── __init__.py
│   └── test_users_api.py    # Автотесты на PyTest + Requests + Allure
├── Dockerfile               # Образ для FastAPI сервиса
├── Dockerfile.tests         # Образ для запуска автотестов
├── docker-compose.yml       # Оркестрация локального запуска
├── requirements-app.txt     # Зависимости микросервиса
├── requirements-tests.txt   # Зависимости тестового фреймворка
└── .gitlab-ci.yml           # CI/CD пайплайн для GitLab

1. Файл requirements-app.txt:

requirements-app.txt 
fastapi==0.110.0
uvicorn==0.28.0
pydantic==2.6.4

2. Файл app/main.py (Исходный код приложения с подробными комментариями):

app/main.py 
from fastapi import FastAPI, HTTPException, status
from pydantic import BaseModel, EmailStr
from typing import Dict, Optional
import uuid

# Инициализируем объект приложения FastAPI
app = FastAPI(
    title="User Management Microservice",
    description="Микросервис управления пользователями для демонстрации Docker + QA",
    version="1.0.0"
)

# Имитируем in-memory базу данных для хранения пользователей
users_db: Dict[str, dict] = {}

# Pydantic схема для входящих данных при создании пользователя
class UserCreateScheme(BaseModel):
    username: str
    email: str
    role: str = "tester"

# Pydantic схема для ответа приложения
class UserResponseScheme(BaseModel):
    id: str
    username: str
    email: str
    role: str
    is_active: bool


# ЭНДПОИНТ 1: Healthcheck (Проверка работоспособности сервиса)
@app.get(
    "/health",
    status_code=status.HTTP_200_OK,
    summary="Healthcheck эндпоинт",
    tags=["Health"]
)
def health_check():
    """Служебный эндпоинт для проверки статуса сервиса из Docker Healthcheck."""
    return {"status": "ok", "service": "user-management-api"}


# ЭНДПОИНТ 2: Создание пользователя (POST /api/v1/users)
@app.post(
    "/api/v1/users",
    response_model=UserResponseScheme,
    status_code=status.HTTP_201_CREATED,
    summary="Создание нового пользователя",
    tags=["Users"]
)
def create_user(user: UserCreateScheme):
    """
    Принимает JSON с параметрами username, email и role.
    Генерирует уникальный UUID и сохраняет пользователя в БД.
    """
    user_id = str(uuid.uuid4())
    new_user = {
        "id": user_id,
        "username": user.username,
        "email": user.email,
        "role": user.role,
        "is_active": True
    }
    users_db[user_id] = new_user
    return new_user


# ЭНДПОИНТ 3: Получение пользователя по ID (GET /api/v1/users/{user_id})
@app.get(
    "/api/v1/users/{user_id}",
    response_model=UserResponseScheme,
    status_code=status.HTTP_200_OK,
    summary="Получение профиля пользователя по ID",
    tags=["Users"]
)
def get_user_by_id(user_id: str):
    """
    Ищет пользователя в БД по переданному user_id.
    Если пользователь найден — возвращает статус 200 и объект пользователя.
    Если не найден — генерирует HTTPException со статусом 404.
    """
    if user_id not in users_db:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail=f"Пользователь с ID '{user_id}' не найден"
        )
    return users_db[user_id]

7. Пишем Dockerfile для FastAPI сервиса

Теперь создадим файл Dockerfile, который описывает, как собрать Docker-образ нашего FastAPI микросервиса. Будем использовать паттерн использования легких дистрибутивов python:3.11-slim.

Dockerfile 
# 1. За основу берем официальный компактный образ Python 3.11 на базе Debian Slim
FROM python:3.11-slim

# 2. Устанавливаем переменные окружения Python:
# PYTHONUNBUFFERED=1 гарантирует мгновенный вывод логов в консоль Docker без кэширования
# PYTHONDONTWRITEBYTECODE=1 запрещает создание .pyc файлов
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

# 3. Задаем рабочей директорией внутри контейнера папку /app
WORKDIR /app

# 4. Сначала копируем ТОЛЬКО файл зависимостей!
# Это критично для эффективного кэширования слоев Docker:
# если код приложения изменится, а зависимости нет — Docker не будет переустанавливать pip пакеты!
COPY requirements-app.txt .

# 5. Устанавливаем зависимости без сохранения кэша pip (флаг --no-cache-dir уменьшает размер образа)
RUN pip install --no-cache-dir -r requirements-app.txt

# 6. Копируем исходный код нашего приложения в контейнер
COPY app/ ./app/

# 7. Открываем порт 8000 (документирование порта для разработчиков)
EXPOSE 8000

# 8. Точка входа: запускаем ASGI сервер uvicorn на адресе 0.0.0.0 (чтобы принимать запросы снаружи контейнера)
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Сборка и ручной запуск FastAPI сервиса:

bash

# Запуск контейнера в фоне с пробросом порта 8000 на локальную машину
docker run -d -p 8000:8000 --name fastapi-app fastapi-service:1.0

# Проверка работоспособности через curl
curl http://localhost:8000/health

Часть 4. Создаем Контейнер с Автотестами (PyTest + Requests + Allure)

Теперь создадим изолированный тестовый фреймворк. Главное правило разработки автотестов в Docker: URL тестируемого сервиса должен передаваться динамически через переменные окружения (Environment Variables), чтобы тесты могли запускаться как локально (`http://localhost:8000`), так и внутри контейнерной сети (`http://fastapi-service:8000`).

1. Файл requirements-tests.txt:

requirements-tests.txt 
pytest==8.1.1
requests==2.31.0
allure-pytest==2.13.5

2. Файл tests/test_users_api.py (Полный комплект тестов с разметкой Allure):

tests/test_users_api.py 
import os
import pytest
import requests
import allure

# Динамически получаем базовый URL сервиса из переменной окружения BASE_URL
# По умолчанию используем localhost:8000 для локального запуска без Docker
BASE_URL = os.getenv("BASE_URL", "http://localhost:8000")


@allure.epic("API Testing")
@allure.feature("User Management Service")
class TestUserApi:

    @allure.story("Healthcheck")
    @allure.title("Проверка доступности сервиса (GET /health)")
    @allure.severity(allure.severity_level.BLOCKER)
    def test_healthcheck_returns_200(self):
        """Тест проверяет, что эндпоинт /health возвращает HTTP 200 OK и статусный JSON."""
        url = f"{BASE_URL}/health"
        
        with allure.step(f"Отправка GET запроса на {url}"):
            response = requests.get(url, timeout=5)
            
        with allure.step("Проверка статус-кода и ответа"):
            assert response.status_code == 200, f"Ожидался 200, получен {response.status_code}"
            data = response.json()
            assert data["status"] == "ok"
            assert data["service"] == "user-management-api"

    @allure.story("Create User")
    @allure.title("Успешное создание нового пользователя (POST /api/v1/users)")
    @allure.severity(allure.severity_level.CRITICAL)
    def test_create_user_success(self):
        """Тест проверяет создание нового пользователя и структуру ответа."""
        url = f"{BASE_URL}/api/v1/users"
        payload = {
            "username": "qa_hero",
            "email": "hero@qalify.ru",
            "role": "automation_lead"
        }
        
        with allure.step("Отправка POST запроса на создание пользователя"):
            response = requests.post(url, json=payload, timeout=5)
            
        with allure.step("Проверка ответа сервера (HTTP 201 Created)"):
            assert response.status_code == 201
            user_data = response.json()
            assert "id" in user_data
            assert user_data["username"] == payload["username"]
            assert user_data["email"] == payload["email"]
            assert user_data["role"] == payload["role"]
            assert user_data["is_active"] is True

    @allure.story("Get User")
    @allure.title("Получение ранее созданного пользователя по ID (GET /api/v1/users/{id})")
    @allure.severity(allure.severity_level.CRITICAL)
    def test_get_user_by_id_success(self):
        """Тест сначала создает пользователя, а затем запрашивает его профиль по ID."""
        # Шаг 1: Создание пользователя
        create_url = f"{BASE_URL}/api/v1/users"
        payload = {"username": "alex_sdet", "email": "alex@qalify.ru", "role": "sdet"}
        create_resp = requests.post(create_url, json=payload, timeout=5)
        created_user_id = create_resp.json()["id"]

        # Шаг 2: Получение профиля по ID
        get_url = f"{BASE_URL}/api/v1/users/{created_user_id}"
        with allure.step(f"Запрос профиля пользователя с ID {created_user_id}"):
            response = requests.get(get_url, timeout=5)
            
        with allure.step("Проверка совпадения данных пользователя"):
            assert response.status_code == 200
            user_data = response.json()
            assert user_data["id"] == created_user_id
            assert user_data["username"] == "alex_sdet"

    @allure.story("Get User Errors")
    @allure.title("Получение несуществующего пользователя возвращает 404 Not Found")
    @allure.severity(allure.severity_level.NORMAL)
    def test_get_nonexistent_user_returns_404(self):
        """Тест передает несуществующий UUID и проверяет обработку ошибки 404."""
        random_id = "non-existent-uuid-99999"
        url = f"{BASE_URL}/api/v1/users/{random_id}"
        
        with allure.step("Отправка запроса с невалидным ID"):
            response = requests.get(url, timeout=5)
            
        with allure.step("Проверка HTTP 404 Not Found"):
            assert response.status_code == 404
            error_data = response.json()
            assert "detail" in error_data
            assert "не найден" in error_data["detail"]

Часть 5. Allure Report в изолированном окружении

Главная сложность при запуске автотестов внутри Docker — сохранение результатов отчетов после завершения работы контейнера. По умолчанию, когда контейнер с тестами завершает работу и останавливается, все созданные внутри него файлы пропадают.

Для решения этой проблемы используются Docker Volumes (Тома) или Bind Mounts (проброс папки хоста). Команда запуска автотестов с сохранением Allure результатов на локальный диск выглядела бы так:

bash 
# Создание bind mount: папка ./allure-results на хосте монтируется в /app/allure-results внутри контейнера
docker run --rm \
  --network="host" \
  -e BASE_URL="http://localhost:8000" \
  -v $(pwd)/allure-results:/app/allure-results \
  autotests-image:1.0

# После завершения генерация красивого HTML отчета на локальной машине:
allure generate ./allure-results --clean -o ./allure-report
allure open ./allure-report

Часть 6. Docker Compose: Запуск в 1 клик

Запускать каждый контейнер вручную через длинные команды docker run неудобно. Docker Compose позволяет описать всю архитектуру (API сервис, баз данных, селенуим-сетку, контейнер с автотестами и Allure) в одном человекочитаемом YAML-файле.

Ключевая задача QA при составлении Compose-файла — правильно настроить порядок запуска (Healthcheck и `depends_on`). Тестовый контейнер не должен начинать выполнение тестов до того, как API сервис полностью скомпилируется и начнет отвечать на HTTP-запросы!

Файл docker-compose.yml (Полный готовый сценарий):

docker-compose.yml 
version: '3.8'

# Объявляем изолированную виртуальную сеть для наших сервисов
networks:
  qa_network:
    driver: bridge

# Объявляем volume для хранения и передаче сырых отчетов Allure
volumes:
  allure_results_data:

services:
  # СЕРВИС 1: Микросервис на FastAPI (System Under Test)
  fastapi-service:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: sut_fastapi_app
    ports:
      - "8000:8000"
    networks:
      - qa_network
    # Настраиваем Healthcheck для автоматической проверки готовности сервиса
    healthcheck:
      test: ["CMD-SHELL", "curl -f http://localhost:8000/health || exit 1"]
      interval: 3s
      timeout: 3s
      retries: 5
      start_period: 2s
    restart: on-failure

  # СЕРВИС 2: Контейнер с автотестами PyTest
  autotests:
    build:
      context: .
      dockerfile: Dockerfile.tests
    container_name: qa_pytest_runner
    environment:
      # Внутри сети Docker обращаться к сервису можно прямо по имени сервиса 'fastapi-service'!
      - BASE_URL=http://fastapi-service:8000
    networks:
      - qa_network
    volumes:
      # Монтируем локальную директорию ./allure-results для сохранения результатов отчета на хосте
      - ./allure-results:/app/allure-results
    # ТРЕБОВАНИЕ: Тесты запускаются СТРОГО ПОСЛЕ того, как fastapi-service станет HEALTHY!
    depends_on:
      fastapi-service:
        condition: service_healthy

  # СЕРВИС 3: Генератор отчетов Allure (Allure Docker Service)
  allure-report:
    image: frankescobar/allure-docker-service:2.21.0
    container_name: qa_allure_server
    environment:
      CHECK_RESULTS_EVERY_SECONDS: 3
      KEEP_HISTORY: "TRUE"
    ports:
      - "5050:5050"
    volumes:
      - ./allure-results:/app/allure-results
    depends_on:
      - autotests

Запуск автотестов в один клик:

bash 
# Магическая команда запуска всего тестового окружения с флагом возврата кода ответа тестов:
docker compose up --build --exit-code-from autotests
🎯 Что происходит при выполнении этой команды:
  1. Docker автоматически собирает два образа (FastAPI и PyTest).
  2. Создает закрытую виртуальную сеть qa_network.
  3. Запускает fastapi-service и начинает опрашивать его healthcheck на /health.
  4. Как только API отвечает 200 OK, Docker Compose стартует autotests.
  5. Тесты выполняются, сохраняют Allure-файлы в смонтированную папку ./allure-results.
  6. Благодаря флагу --exit-code-from autotests, весь процесс возвращает код завершения 0 (если все тесты прошли) или 1 (если упал хотя бы 1 тест). Это идеально для CI/CD!

Часть 7. Запуск в Пайплайне GitLab CI с Нуля

Теперь перенесем наш стек в реальный CI/CD пайплайн на платформе GitLab CI. Мы напишем конфигурацию .gitlab-ci.yml с использованием технологии Docker-in-Docker (dind).

Пайплайн будет состоять из 3 последовательных стадий (stages):

  • test — Сборка и запуск тестового окружения через Docker Compose.
  • reports — Сборка красивого HTML отчета Allure из артефактов.
  • deploy — Публикация HTML отчета Allure на GitLab Pages.

Полный файл .gitlab-ci.yml:

.gitlab-ci.yml 
# Список стадий выполнения CI/CD пайплайна
stages:
  - test
  - reports
  - deploy

# Глобальные переменные для работы Docker-in-Docker (dind)
variables:
  DOCKER_HOST: tcp://docker:2375
  DOCKER_TLS_CERTDIR: ""
  DOCKER_DRIVER: overlay2

# СТАДИЯ 1: Запуск автоматизированных тестов в Docker Compose
run_autotests:
  stage: test
  image: docker:24.0.5
  services:
    - name: docker:24.0.5-dind
      entrypoint: ["dockerd-entrypoint.sh"]
      command: ["--tls=false"]
  before_script:
    # Устанавливаем docker-compose CLI утилиту
    - apk add --no-cache docker-compose
    # Проверяем доступность Docker демона
    - docker info
  script:
    - echo "🚀 Запуск тестового окружения и прогон PyTest..."
    # Запускаем Compose стек. При падении тестов шаг завершится с ошибкой
    - docker-compose up --build --exit-code-from autotests
  after_script:
    - echo "🧹 Очистка контейнеров..."
    - docker-compose down -v
  artifacts:
    # Сохраняем сгенерированные сырые данные Allure как артефакт пайплайна
    name: "allure-results-$CI_COMMIT_REF_SLUG"
    when: always
    expire_in: 7 days
    paths:
      - allure-results/

# СТАДИЯ 2: Генерация HTML отчета Allure
generate_allure_report:
  stage: reports
  image: frankescobar/allure-docker-service:2.21.0
  when: always
  script:
    - echo "📊 Генерация статичного HTML отчета Allure..."
    # Команда генерации отчета из входной папки allure-results в папку allure-report
    - allure generate allure-results --clean -o public
  artifacts:
    name: "allure-html-report"
    when: always
    expire_in: 30 days
    paths:
      - public/

# СТАДИЯ 3: Публикация отчета на GitLab Pages
pages:
  stage: deploy
  image: alpine:latest
  when: always
  script:
    - echo "🌐 Публикация Allure отчета на GitLab Pages..."
    - ls -la public/
  artifacts:
    paths:
      - public
  only:
    - main
    - master
💡 Важное отличие в CI: Благодаря секции artifacts: when: always, сырые данные Allure и итоговый HTML-отчет сохраняются в GitLab даже если автотесты упали с падающими ассертами! Вы всегда сможете открыть готовую ссылку на GitLab Pages и детально проанализировать скриншоты и ошибки.

Часть 8. Чек-лист и Best Practices Docker для QA

⚡ Золотые правила работы с Docker в автотестировании:
  • ✔
    Используйте `.dockerignore`: Исключайте из контекста сборки папки .git, .pytest_cache, __pycache__, venv и .env. Это ускоряет сборку в разы!
  • ✔
    Фиксируйте версии (Pinning Versions): Никогда не используйте тег python:latest в продакшн Dockerfile. Указывайте точные версии: python:3.11-slim, postgres:15.4-alpine.
  • ✔
    Используйте slim и alpine версии: Базовый образ Ubuntu весит ~800MB, а Debian Slim или Alpine — от 50MB до 150MB.
  • ✔
    Настраивайте Healthcheck: Никогда не надейтесь на задержки sleep 10. Используйте healthcheck сервисов в Docker Compose.
  • ✔
    Очищайте неиспользуемые ресурсы: Регулярно запускайте docker system prune -af --volumes на тестовых раннерах CI.

Заключение

Контейнеризация тестовых окружений с помощью Docker и Docker Compose переводит автоматизацию тестирования на абсолютно новый уровень зрелости. Вы получаете полностью герметичную, изолированную и легко масштабируемую систему, которая запускается буквально одной командой как на ноутбуке QA инженера, так и в CI/CD пайплайне GitLab.

Применяйте описанный паттерн в своих проектах, экономьте время команды и забудьте о нестабильных окружениях раз и навсегда!
