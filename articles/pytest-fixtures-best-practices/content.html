Фикстуры в PyTest — это центральный фундамент, на котором строится современный, устойчивый и чистый тестовый фреймворк на языке Python. В отличие от традиционных xUnit-фреймворков (таких как unittest), где логика подготовки и очистки жестко привязана к методам setUp() и tearDown(), PyTest предлагает концепцию Внедрения Зависимостей (Dependency Injection). В этом исчерпывающем руководстве мы пройдем путь от написания первой базовой фикстуры до построения сложных граф-зависимостей, интеграции с БД, браузерами и CI/CD пайплайнами.

Часть 1. Анатомия фикстуры и Внедрение Зависимостей

В PyTest фикстура — это функция, помеченная декоратором @pytest.fixture. Фикстуры подготавливают окружение (создают объекты, подключаются к базе данных, поднимают браузер, генерируют тестовые данные) и передают результат в автотест.

Главная особенность PyTest — Dependency Injection (Внедрение Зависимостей) по имени аргумента. Вам не нужно явно вызывать фикстуру; достаточно указать имя фикстуры в параметрах тестовой функции, и PyTest сам найдет её, выполнит и передаст возвращаемое значение.

test_basic_fixture.py 
import pytest

@pytest.fixture
def sample_user():
    """Простая фикстура, возвращающая словарь с данными пользователя."""
    return {
        "username": "alex_qa",
        "email": "alex@qalify.ru",
        "role": "admin"
    }

def test_user_role(sample_user):
    # PyTest автоматически сопоставляет имя аргумента 'sample_user' с объявленной фикстурой
    assert sample_user["role"] == "admin"
    assert "@" in sample_user["email"]

Return vs Yield: Безопасный Setup и Teardown

Если фикстуре нужно не только подготовить ресурсы (Setup), но и очистить их после окончания теста (Teardown), в Python используется ключевое слово yield вместо return.

  • Код ДО yield: Выполняется перед запуском теста (Setup).
  • Значение после yield: Передается в тестовую функцию как аргумент.
  • Код ПОСЛЕ yield: Выполняется СТРОГО после завершения теста (Teardown) — даже если тест упал с ошибкой!
💡 Гарантия выполнения Teardown: Блок кода после yield аналогичен блоку finally. PyTest гарантирует, что шаги очистки будут выполнены независимо от статуса прохождения теста (PASS, FAIL, ERROR).
test_yield_fixture.py 
import pytest
import tempfile
import os

@pytest.fixture
def temp_file():
    # --- SETUP: Создаем временный файл ---
    temp_dir = tempfile.mkdtemp()
    file_path = os.path.join(temp_dir, "test_data.txt")
    with open(file_path, "w", encoding="utf-8") as f:
        f.write("QAlify PyTest Guide")
    
    print(f"\n[SETUP] Создан временный файл: {file_path}")
    
    # Передаем путь к файлу в тест
    yield file_path
    
    # --- TEARDOWN: Удаляем файл и директорию после теста ---
    print(f"\n[TEARDOWN] Удаление ресурса: {file_path}")
    if os.path.exists(file_path):
        os.remove(file_path)
    os.rmdir(temp_dir)

def test_read_temp_file(temp_file):
    with open(temp_file, "r", encoding="utf-8") as f:
        content = f.read()
    assert content == "QAlify PyTest Guide"

Часть 2. Области видимости (Scopes) и управление жизненным циклом

Область видимости (Scope) определяет, как часто PyTest будет создавать и уничтожать экземпляр фикстуры. Правильный выбор скоупа позволяет экономить время прогона тестов в десятки раз за счет повторного использования «тяжелых» ресурсов.

В PyTest доступно 5 областей видимости:

Scope (Область) Частота создания (Lifecycle) Типичное применение
function (default) Перед каждым тестом, очистка после каждого теста. Изолированные тестовые данные, моки, транзакции БД.
class Один раз на весь тестовый класс (class TestX). Общие UI-страницы для группы тестов одного компонента.
module Один раз на весь файл с тестами (test_*.py). HTTP-сессии, подготовка тестового файла или конфига.
package Один раз на всю директорию-пакет с тестами. Интеграционные сервисы для группы связанных модулей.
session Один раз на весь прогон тестовой сюиты (Test Suite). Запуск браузера, глобальное подключение к БД, Docker Compose.
test_scopes_demo.py 
import pytest

@pytest.fixture(scope="session")
def db_connection():
    print("\n>>> [SESSION SETUP] Подключение к PostgreSQL...")
    connection = {"status": "connected", "db": "qa_db"}
    yield connection
    print("\n<<< [SESSION TEARDOWN] Закрытие подключения к PostgreSQL")

@pytest.fixture(scope="module")
def api_client():
    print("\n  >> [MODULE SETUP] Инициализация HTTP клиента")
    yield {"base_url": "https://api.qalify.ru"}
    print("\n  << [MODULE TEARDOWN] Закрытие HTTP сессии")

@pytest.fixture(scope="function")
def user_payload():
    print("\n    > [FUNCTION SETUP] Генерация случайного юзера")
    yield {"id": 101, "name": "Alice"}
    print("\n    < [FUNCTION TEARDOWN] Очистка юзера")

def test_api_first(db_connection, api_client, user_payload):
    assert db_connection["status"] == "connected"
    assert api_client["base_url"] == "https://api.qalify.ru"

def test_api_second(db_connection, api_client, user_payload):
    assert user_payload["id"] == 101

Динамический Scope (Callable Scope)

Начиная с PyTest 5.2, область видимости фикстуры может быть динамической. Вместо строки ("session") в параметр scope можно передать функцию, которая принимает fixture_name и config, возвращая нужный скоуп на основе флагов командной строки.

💡 Практическая польза: При локальной отладке вам может потребоваться пересоздавать БД перед каждым тестом (scope="function"), а на CI/CD сервере — переиспользовать единый стенд на всю сессию (scope="session").
conftest_dynamic_scope.py 
import pytest

def determine_db_scope(fixture_name, config):
    # Если передан CLI флаг --reuse-db, используем session скоуп, иначе function
    if config.getoption("--reuse-db", default=False):
        return "session"
    return "function"

def pytest_addoption(parser):
    parser.addoption("--reuse-db", action="store_true", help="Повторно использовать БД между тестами")

@pytest.fixture(scope=determine_db_scope)
def database(request):
    print(f"\n[DB FIXTURE] Запуск фикстуры со скоупом: {request.scope}")
    yield "db_instance"

Часть 3. Продвинутые возможности и суперспособности

1. Параметризация фикстур (`params` & `ids`)

Параметризация фикстур — это один из самых мощных механизмов PyTest, позволяющий мультиплицировать прогон автотестов без дублирования кода. Передавая параметр params в декоратор @pytest.fixture, вы заставляете PyTest запустить все тесты, использующие эту фикстуру, столько раз, сколько элементов содержится в списке params.

🔍 Детальный разбор компонентов:
  • params (список значений): Передает наборы данных или объектов в фикстуру. Внутри самой фикстуры текущий элемент извлекается через служебный объект request.param.
  • ids (идентификаторы итераций): Отвечает за человекочитаемое именование тестов в отчетах PyTest, Allure и IDE (вместо невнятных test_api[param0], test_api[param1]).

За что конкретно отвечает params?

Когда вы объявляете @pytest.fixture(params=[val1, val2, val3]), PyTest на этапе сбора тестов (Collection Phase) генерирует 3 копии каждого автотеста, принимающего эту фикстуру. При запуске первой копии фикстура получит `val1`, при втором — `val2`, при третьем — `val3`.

За что конкретно отвечает ids?

По умолчанию PyTest формирует имя теста в консоли путем вызова str(param). Но если в `params` передаются сложные словари, экземпляры классов или кортежи, автосгенерированные имена в отчетах превращаются в неудобный набор символов. Параметр ids решает эту проблему и поддерживает два формата:

  • Список строк: Массив понятных названий той же длины, что и `params` (например, ids=["Chrome-Desktop", "Firefox-Mobile"]).
  • Функция-колбэк (Callable): Функция, которая принимает текущий элемент `param` и возвращает понятное строковое имя на лету (например, ids=lambda db: f"DB_{db['engine']}").

Сравнение: `@pytest.mark.parametrize` vs `params` в фикстуре

Инструмент Область применения Когда выбирать
@pytest.mark.parametrize Локальная параметризация конкретной тестовой функции. Проверка разных наборов граничных входных данных в 1 конкретном тесте.
@pytest.fixture(params=...) Глобальная параметризация окружения на уровне фикстуры. Прогон ВСЕЙ сюиты тестов в разных браузерах, под разными ролями пользователей или на разных БД.
test_fixture_parametrization_advanced.py 
import pytest

# Сложные объекты конфигурации окружений
ENV_CONFIGS = [
    {"env": "staging", "url": "https://staging.api.qalify.ru", "db_port": 5432},
    {"env": "production", "url": "https://api.qalify.ru", "db_port": 6432}
]

# Способ 1: Использование списка строк в ids
@pytest.fixture(params=ENV_CONFIGS, ids=["Staging-Environment", "Production-Environment"])
def env_client(request):
    # Доступ к текущему словарю через request.param
    config = request.param
    print(f"\n[SETUP] Подключение к стенду: {config['env']} ({config['url']})")
    yield config
    print(f"\n[TEARDOWN] Отключение от стенда {config['env']}")

# Способ 2: Использование функции-лямбды в ids для динамического имени
BROWSERS = [{"name": "Chromium", "headless": True}, {"name": "Firefox", "headless": True}]

@pytest.fixture(params=BROWSERS, ids=lambda b: f"Browser-{b['name']}")
def browser_config(request):
    return request.param

def test_api_health_check(env_client):
    # Данный тест автоматически выполнится 2 раза (Staging-Environment и Production-Environment)
    assert env_client["db_port"] in [5432, 6432]

def test_ui_rendering(browser_config):
    # Имя итерации в консоли и Allure отчете: test_ui_rendering[Browser-Chromium]
    assert browser_config["headless"] is True

2. Автоматические фикстуры (`autouse=True`)

Параметр autouse=True заставляет PyTest автоматически активировать фикстуру для всех тестов в зоне её видимости — даже если тест явно не запрашивает её в параметрах.

⚠️ Опасность злоупотребления autouse:
Использование autouse=True создает «неявное поведение» (Magic). Если заупотреблять им, инженеры перестанут понимать, почему меняются глобальные переменные или сбрасываются состояния. Применяйте autouse строго для фоновых сервисных задач (сброс переменной окружения, замер времени выполнения, очистка кэша).
test_autouse_timer.py 
import pytest
import time

@pytest.fixture(autouse=True)
def print_test_timer(request):
    """Автоматически измеряет время выполнения каждого теста в проекте."""
    start_time = time.time()
    yield
    duration = time.time() - start_time
    print(f"\n⏱️ Тест '{request.node.name}' выполнен за {duration:.4f} сек")

3. Встроенная фикстура `request` и finalizers

Встроенная фикстура request предоставляет интроспекцию — полную информацию о текущем исполняемом тесте, включая имя функции, класс, маркировки (markers), параметры и директории.

Кроме yield, очистку ресурсов можно зарегистрировать через метод request.addfinalizer(). Преимущество финализаторов в том, что можно добавить несколько независимых шагов очистки, и все они гарантированно выполнятся по принципу LIFO (Last In, First Out).

test_request_finalizer.py 
import pytest

@pytest.fixture
def managed_resource(request):
    print(f"\nЗапуск подготавливающей фикстуры для теста: {request.node.name}")

    def cleanup_a():
        print("-> [Finalizer A] Очистка первой подсистемы")

    def cleanup_b():
        print("-> [Finalizer B] Очистка второй подсистемы")

    # Регистрируем финализаторы
    request.addfinalizer(cleanup_a)
    request.addfinalizer(cleanup_b)

    return "resource_payload"

4. Фабрики фикстур (Fixture Factories)

Стандартная фикстура передает готовый статичный объект. Но что делать, если автотесту требуется создать 3 разных пользователя с уникальными параметрами (например, одного админа, одного заблокированного юзера и одного гостя)?

Для этого применяется паттерн Fixture Factory: фикстура возвращает не значение, а внутреннюю функцию-фабрику.

test_fixture_factory.py 
import pytest

@pytest.fixture
def user_factory():
    created_users = []

    def _create_user(username: str, role: str = "USER", is_active: bool = True):
        user = {
            "id": len(created_users) + 1,
            "username": username,
            "role": role,
            "is_active": is_active
        }
        created_users.append(user)
        return user

    yield _create_user

    # Teardown: удаляем всех созданных через фабрику пользователей в конце теста
    print(f"\nУдаление {len(created_users)} тестовых пользователей из системы...")
    created_users.clear()

def test_multiple_users_creation(user_factory):
    # Создем динамические объекты прямо в теле теста с нужными аргументами
    admin = user_factory(username="root", role="ADMIN")
    banned = user_factory(username="hacker", is_active=False)

    assert admin["role"] == "ADMIN"
    assert banned["is_active"] is False
    assert admin["id"] != banned["id"]

Часть 4. Архитектура conftest.py, Переопределение и Хуки

Файл conftest.py — это специальный модуль PyTest для хранения глобальных фикстур и плагинов. Важная особенность: фикстуры из conftest.py доступны всем тестам в текущей и дочерних директориях без явного импорта.

Структурное дерево conftest.py 
tests/
│
├── conftest.py                   # Глобальные фикстуры (DB session, API client, Allure hooks)
│
├── unit/
│   ├── conftest.py              # Моки для Unit-тестов
│   └── test_logic.py
│
└── integration/
    ├── conftest.py              # Подключение к тестовому стенду Staging
    └── test_payments.py

Переопределение (Shadowing) фикстур

PyTest ищет фикстуры по иерархии снизу вверх. Фикстура, объявленная в дочернем conftest.py или внутри самого тестового файла, переопределяет фикстуру с таким же именем из родительского conftest.py. Это позволяет изолировать специфическое поведение на уровне отдельных подсистем.

Интеграция фикстуры с PyTest Hooks (Скриншот при падении)

Связывая фикстуры с PyTest-хуками (например, pytest_runtest_makereport), можно создавать мощные механики отладки, например, автоснятие скриншота упавшего UI-теста в Allure отчёт.

conftest_allure_screenshot.py 
import pytest

# Передаем статус выполнения теста в объект node
@pytest.hookimpl(tryfirst=True, hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    rep = outcome.get_result()
    setattr(item, "rep_" + rep.when, rep)

@pytest.fixture
def page_with_screenshot(page, request):
    yield page
    # Проверяем, упал ли тест на этапе исполнения (call)
    if hasattr(request.node, "rep_call") and request.node.rep_call.failed:
        print(f"\n[HOOK] Тест {request.node.name} упал! Делаем скриншот...")
        screenshot_bytes = page.screenshot(full_page=True)
        # Если подключен allure: allure.attach(screenshot_bytes, name="failure_screenshot", attachment_type=PNG)

Часть 5. Реальные рецепты из Real-World QA

1. UI Тестирование: Playwright / Selenium менеджмент

В UI-автоматизации критически важно правильно разделить скоупы: браузер запускается один раз на сессию (дорогой шаг), а контексты и страницы изолируются для каждого теста.

conftest_playwright_architecture.py 
import pytest
from playwright.sync_api import sync_playwright

@pytest.fixture(scope="session")
def browser_instance():
    """Единый запуск браузера на всю сессию прогона."""
    with sync_playwright() as p:
        browser = p.chromium.launch(headless=True)
        yield browser
        browser.close()

@pytest.fixture(scope="function")
def isolated_page(browser_instance):
    """Каждый тест получает чистый инкогнито-контекст и новую вкладку."""
    context = browser_instance.new_context(viewport={"width": 1920, "height": 1080})
    page = context.new_page()
    
    yield page
    
    # Закрытие контекста удаляет все cookies и LocalStorage
    context.close()

2. API Тестирование: Авторизованная сессия + Auto-Clean

Рецепт для API-тестов: авторизация выполняется единожды, а созданные объекты удаляются вызовом API DELETE в блоке yield.

test_api_fixtures.py 
import pytest
import requests

@pytest.fixture(scope="session")
def api_session():
    """Сессия с преднастроенными заголовками и токеном авторизации."""
    session = requests.Session()
    session.headers.update({"Authorization": "Bearer SECRET_JWT_TOKEN", "Content-Type": "application/json"})
    yield session
    session.close()

@pytest.fixture
def created_product(api_session):
    """Создает товар через API и автоматически удаляет его после окончания теста."""
    response = api_session.post("https://api.example.com/v1/products", json={"name": "Test Phone", "price": 49900})
    product_id = response.json()["id"]
    
    yield response.json()
    
    # Clean-up запрос
    api_session.delete(f"https://api.example.com/v1/products/{product_id}")

def test_product_details(api_session, created_product):
    res = api_session.get(f"https://api.example.com/v1/products/{created_product['id']}")
    assert res.status_code == 200
    assert res.json()["name"] == "Test Phone"

3. Database Тестирование: Быстрый транзакционный откат (ROLLBACK)

Самый быстрый способ тестировать работу с базой данных — не очищать таблицы через TRUNCATE, а заворачивать каждый тест в транзакцию и откатывать её (ROLLBACK) после завершения.

test_db_transaction_rollback.py 
import pytest
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

ENGINE = create_engine("postgresql://qa_user:pass@localhost:5432/test_db")
SessionLocal = sessionmaker(bind=ENGINE)

@pytest.fixture(scope="session")
def db_engine():
    return ENGINE

@pytest.fixture
def db_session(db_engine):
    """Создает соединение и внешнюю транзакцию, которая всегда откатывается."""
    connection = db_engine.connect()
    transaction = connection.begin()
    session = SessionLocal(bind=connection)

    yield session

    session.close()
    # Откат транзакции гарантирует 100% первозданную чистоту БД после любого теста!
    transaction.rollback()
    connection.close()

Часть 6. Антипаттерны, Сводная таблица и Чек-лист

❌ Главные антипаттерны при работе с фикстурами:
  • 1. "God Fixture" (Фикстура-Вседержец): Одна огромная фикстура, которая выполняет сразу 15 не связанных шагов (авторизация + БД + моки + создание товаров). Разбивайте её на мелкие атомарные фикстуры!
  • 2. Мутация состояния в Session/Module Scope: Изменение одного и того же объекта фикстуры с уровнем `session` в разных тестах. Это приводит к флакающим тестам (Flaky Tests), зависящим от порядка запуска.
  • 3. Забытый Teardown: Создание ресурсов во внешней системе без кода очистки в `yield`. Стенд быстро замусоривается артефактами.
  • 4. Избыточный `autouse=True`: Применение `autouse` для вещей, специфичных лишь для части тестов.
Признак Хорошая фикстура (Best Practice) Плохая фикстура (Anti-pattern)
Размер & Ответственность Выполняет 1 атомарную задачу (Single Responsibility). Настраивает всю систему сразу в 100 строк кода.
Именование Отражает сущность/ресурс (auth_token, db_session). Глаголы действия или невнятные имена (setup_all, fix1).
Очистка ресурсов Явная очистка через yield или addfinalizer. Отсутствует (данные остаются в БД навсегда).
Изоляция Возвращает уникальные данные или свежий контекст. Возвращает мутируемый глобальный объект без копирования.
💡 Золотой чек-лист идеальной фикстуры:
1. Каждая фикстура делает только ОДНО действие.
2. Скоуп выбран исходя из тяжести создания ресурса (БД/Браузер — `session`, Данные — `function`).
3. Код после `yield` гарантированно чистит то, что создал код до `yield`.
4. Фикстуры лежат в `conftest.py` подходящего уровня вложенности.
5. Для создания множества родственных тестовых данных используются Фабрики Фикстур.
