Часть 1. Классические паттерны GoF в автоматизации

1. Singleton (Одиночка)

Зачем нужен: Гарантирует наличие ровно одного экземпляра объекта во всей системе и предоставляет к нему глобальную точку доступа.

💡 Применение в автотестах: Применяется для управления единым подключением к БД, глобальной конфигурацией тестового стенда (ConfigManager) или пулом логгеров. Гарантирует, что файл настроек читается ровно один раз и защищен от случайного переопределения во время прогона.
singleton_config.py 
# Паттерн Singleton на Python для менеджера конфигурации
class ConfigManager:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super(ConfigManager, cls).__new__(cls)
            # Инициализация единых настроек
            cls._instance.base_url = "https://staging.example.com"
            cls._instance.timeout = 15
            cls._instance.browser = "chromium"
        return cls._instance

# Использование в автотестах:
config1 = ConfigManager()
config2 = ConfigManager()

assert config1 is config2  # Истинный Singleton: один и тот же объект в памяти

2. Builder (Строитель / Test Data Builder)

Зачем нужен: Позволяет пошагово конструировать сложные объекты тестовых данных с разумными значениями по умолчанию.

💡 Применение в автотестах: Применяется для генерации сложных тестовых данных (пользователи, банковские транзакции, заказы в интернет-магазине). Позволяет создавать объекты с корректными дефолтными атрибутами и менять только нужные свойства в один клик.
test_data_builder.py 
# Паттерн Builder для генерации случайного пользователя
from dataclasses import dataclass

@dataclass
class User:
    username: str
    email: str
    role: str
    is_active: bool

class UserBuilder:
    def __init__(self):
        # Дефолтные валидные значения
        self._username = "test_user_99"
        self._email = "user99@example.com"
        self._role = "USER"
        self._is_active = True

    def with_role(self, role: str):
        self._role = role
        return self  # Fluent-интерфейс

    def as_inactive(self):
        self._is_active = False
        return self

    def build(self) -> User:
        return User(
            username=self._username,
            email=self._email,
            role=self._role,
            is_active=self._is_active
        )

# Использование в тесте:
admin_user = UserBuilder().with_role("ADMIN").build()
banned_user = UserBuilder().as_inactive().build()

3. Facade (Фасад)

Зачем нужен: Предоставляет простой единый интерфейс к сложной подсистеме из множества сервисов.

💡 Применение в автотестах: Применяется для скрытия сложных процедур предустановки состояния (Pre-conditions). Объединяет вызовы REST API, прямые запросы к БД и перехват почтовых сервисов в одну понятную строчку метода перед вызовом UI-теста.
user_registration_facade.py 
# Паттерн Facade объединяет работу с API, БД и Почтой
class RegistrationFacade:
    def __init__(self, api_client, db_client, email_service):
        self.api = api_client
        self.db = db_client
        self.email = email_service

    def register_and_verify_user(self, user_data) -> int:
        # 1. Отправляем запрос на регистрацию через API
        user_id = self.api.post_user(user_data)
        
        # 2. Перехватом из почтового сервиса получаем токен
        token = self.email.get_verification_token(user_data.email)
        
        # 3. В БД активируем пользователя напрямую
        self.db.set_user_active(user_id, token)
        return user_id

# В автотесте весь сложный процесс выполняется в одну понятную строчку:
user_id = facade.register_and_verify_user(test_user)

4. Factory (Фабрика / Factory Method)

Зачем нужен: Делегирует создание объектов специальному классу-фабрике на основе входных параметров.

💡 Применение в автотестах: Применяется для динамической инициализации браузерных драйверов (Chromium, Firefox, WebKit, эмуляторы мобильных устройств) на основе флагов командной строки CI/CD или файлов конфигурации (pytest --browser=firefox).
browser_factory.py 
# Паттерн Factory Method для создания инстансов браузеров
class BrowserFactory:
    @staticmethod
    def create_browser(playwright_instance, browser_type: str = "chromium"):
        browser_type = browser_type.lower()
        if browser_type == "chromium":
            return playwright_instance.chromium.launch(headless=True)
        elif browser_type == "firefox":
            return playwright_instance.firefox.launch(headless=True)
        elif browser_type == "webkit":
            return playwright_instance.webkit.launch(headless=True)
        else:
            raise ValueError(f"Неподдерживаемый тип браузера: {browser_type}")

# Использование в PyTest фикстуре:
browser = BrowserFactory.create_browser(p, config.browser_name)

Часть 2. Специализированные паттерны тестирования UI

5. Page Object Model (POM)

Зачем нужен: Фундаментальный паттерн UI-автоматизации. Каждая страница представляется в виде класса, где поля — это селекторы, а методы — действия пользователя.

💡 Применение в автотестах: Применяется для изоляции структуры веб-страниц от проверок в тестах. Изменение верстки или селекторов на фронтенде правится в одном месте в классе страницы, а не в сотне автотестов.
login_page_pom.py 
# Паттерн Page Object Model (Playwright Python)
from playwright.sync_api import Page, expect

class LoginPage:
    def __init__(self, page: Page):
        self.page = page
        self._username_input = page.locator("#username")
        self._password_input = page.locator("#password")
        self._login_button = page.locator("#btn-submit")
        self._error_message = page.locator(".alert-danger")

    def navigate(self):
        self.page.goto("https://example.com/login")

    def login(self, username: str, password: str):
        self._username_input.fill(username)
        self._password_input.fill(password)
        self._login_button.click()

    def should_show_error(self, expected_text: str):
        expect(self._error_message).to_contain_text(expected_text)

6. Page Factory (Ленивая фабрика элементов)

Зачем нужен: Исторический паттерн из экосистемы Java Selenium, предназначенный для отложенной (ленивой) инициализации веб-элементов на странице.

⚠️ Почему Page Factory — это Java-паттерн и не применяется в Python:
  • В Java: PageFactory является нативным классом из официальной библиотеки org.openqa.selenium.support.PageFactory. Он использует аннотации @FindBy для автоинициализации элементов через прокси-объекты.
  • В Python: Нативной библиотеки Page Factory не существует. Попытки слепо скопировать аннотации Java в Python с помощью сторонних пакетов считаются непитоничными (unpythonic).
  • В Playwright Python: Локаторы page.locator("#username") уже являются ленивыми из коробки. При объявлении локатор НЕ ищет элемент в DOM, а обращается к браузеру только в момент вызова действия (.click(), .fill()). Специальные обертки Page Factory в Python просто не нужны.

Классический пример на Java (где паттерн нативен):

LoginPageFactory.java 
// Нативная реализация Page Factory в Java Selenium
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.WebElement;
import org.openqa.selenium.support.FindBy;
import org.openqa.selenium.support.PageFactory;

public class LoginPageFactory {
    private WebDriver driver;

    // Аннотации @FindBy ищут элементы лениво при вызове
    @FindBy(id = "username")
    private WebElement usernameInput;

    @FindBy(id = "password")
    private WebElement passwordInput;

    @FindBy(id = "submit-btn")
    private WebElement submitButton;

    public LoginPageFactory(WebDriver driver) {
        this.driver = driver;
        // Инициализация элементов прокси-объектами
        PageFactory.initElements(driver, this);
    }

    public void login(String user, String pass) {
        usernameInput.sendKeys(user);
        passwordInput.sendKeys(pass);
        submitButton.click();
    }
}

Питонический эквивалент на Python (через @property):

page_factory_pythonic.py 
# Питонический аналог ленивого поиска элементов на Python
class DashboardPage:
    def __init__(self, page):
        self.page = page

    # В Python вычисляемые свойства @property выполняют роль ленивой фабрики
    @property
    def user_profile_badge(self):
        # Ищется в DOM строго в момент обращения: page.user_profile_badge
        return self.page.locator(".user-profile-badge")

    @property
    def logout_button(self):
        return self.page.locator("#logout-btn")

    def logout(self):
        self.logout_button.click()
💡 Применение в автотестах: Применяется для отложенного (ленивого) поиска динамических элементов на AJAX/SPA страницах. Селекторы не ищутся при создании объекта страницы, а запрашиваются у браузера ровно в момент выполнения шага теста.

7. Page Element (Component Object / Atomic Design)

Зачем нужен: Разбивает гигантские Page Object классы на мелкие переиспользуемые UI-компоненты (шапка сайта, меню, таблицы, модальные окна).

💡 Применение в автотестах: Применяется для моделирования сквозных интерфейсных элементов (шапка сайта, боковое меню, таблицы данных, модалки), которые повторяются на десятках разных страниц системы.
page_element_component.py 
# Паттерн Page Element / Component Object
class HeaderComponent:
    def __init__(self, root_locator):
        self._root = root_locator
        self.search_input = self._root.locator("input[type='search']")
        self.cart_icon = self._root.locator(".cart-icon")

    def search_for(self, query: str):
        self.search_input.fill(query)
        self.search_input.press("Enter")

class HomePage:
    def __init__(self, page):
        self.page = page
        # Встраиваем компонент шапки сайта в объект страницы
        self.header = HeaderComponent(page.locator("header.site-header"))

8. Page Builder (Строитель динамических страниц)

Зачем нужен: Предназначен для создания динамических конфигураций страниц во время выполнения. Этот паттерн решает проблему, когда веб-интерфейс состоит из произвольного набора виджетов (например, кастомизируемые дашборды, CMS-системы, Tilda, Notion), и создавать отдельный Page Object под каждую комбинацию блоков бессмысленно.

💡 Применение в автотестах: Применяется при тестировании конструкторов сайтов и кастомных веб-панелей (CMS, Tilda, Notion, админки), где структура страницы собирается из произвольного набора пользовательских блоков прямо на лету.

Ниже представлен полный пример: сначала мы определяем компоненты-виджеты, затем строитель `DashboardPageBuilder`, и показываем, **как автотест обращается к собранной странице**.

test_page_builder_usage.py 
# 1. Компоненты-виджеты для сборки
class HeaderComponent:
    def __init__(self, locator):
        self.locator = locator
    def search(self, text):
        self.locator.locator("input").fill(text)

class TableWidgetComponent:
    def __init__(self, locator):
        self.locator = locator
    def get_row_count(self):
        return self.locator.locator("tr").count()

class AnalyticsWidgetComponent:
    def __init__(self, locator):
        self.locator = locator
    def get_total_sales(self):
        return self.locator.locator(".sales-value").inner_text()


# 2. Динамический объект страницы, хранящий список собранных виджетов
class DynamicDashboardPage:
    def __init__(self, page, widgets: dict):
        self.page = page
        self.widgets = widgets

    def widget(self, name: str):
        """Возвращает нужный виджет на странице по его имени"""
        return self.widgets[name]


# 3. Строитель страницы (Page Builder)
class DashboardPageBuilder:
    def __init__(self, page):
        self.page = page
        self._widgets = {}

    def with_header(self):
        self._widgets["header"] = HeaderComponent(self.page.locator("header"))
        return self

    def with_table(self, container_selector: str):
        self._widgets["table"] = TableWidgetComponent(self.page.locator(container_selector))
        return self

    def with_analytics(self, container_selector: str):
        self._widgets["analytics"] = AnalyticsWidgetComponent(self.page.locator(container_selector))
        return self

    def build(self) -> DynamicDashboardPage:
        """Сборка готового объекта страницы"""
        return DynamicDashboardPage(self.page, self._widgets)


# =====================================================================
# 4. Использование в автотесте: сборка и обращение к элементам
# =====================================================================
def test_user_custom_dashboard(page):
    page.goto("https://example.com/dashboard")

    # Сборка кастомного дашборда пользователя из 3 блоков
    dashboard = (
        DashboardPageBuilder(page)
        .with_header()
        .with_analytics("#sales-widget-container")
        .with_table("#recent-orders-table")
        .build()
    )

    # Обращение к элементам динамически собранной страницы в тесте:
    dashboard.widget("header").search("Отчет за июль")
    
    sales_total = dashboard.widget("analytics").get_total_sales()
    assert sales_total == "1 500 000 ₽"

    rows_count = dashboard.widget("table").get_row_count()
    assert rows_count > 0

Часть 3. Популярные продвинутые паттерны в QA 🚀

9. Fluent Interface (Цепочечные вызовы)

Зачем нужен: Методы классов возвращают `self` или следующий Page Object, формируя естественный легкочитаемый DSL.

💡 Применение в автотестах: Применяется для создания выразительного предметно-ориентированного языка (DSL) автотестов. Позволяет писать сценарии в виде непрерывных цепочек вызовов, читаемых как естественный английский текст.
fluent_interface.py 
# Паттерн Fluent Interface (Method Chaining)
class FluentLoginPage:
    def __init__(self, page):
        self.page = page

    def enter_username(self, username: str):
        self.page.fill("#user", username)
        return self  # Возвращаем тот же объект

    def enter_password(self, password: str):
        self.page.fill("#pass", password)
        return self

    def submit_and_go_to_dashboard(self):
        self.page.click("#submit")
        return DashboardPage(self.page)  # Переходим к следующему Page Object

# Красивое использование в автотесте:
dashboard = (
    FluentLoginPage(page)
    .enter_username("admin")
    .enter_password("secret")
    .submit_and_go_to_dashboard()
)

10. Screenplay Pattern (Паттерн Актер-Задача)

Зачем нужен: Состоит из Актеров (Actors), их Способностей (Abilities), Задач (Tasks) и Вопросов (Questions).

💡 Применение в автотестах: Применяется при масштабировании фреймворков тестирования в крупных командах с десятками QA. Четко разделяет Актеров, их Способности и Задачи, исключая появление раздутых классов-гигантов и дублирование сценариев.
screenplay_pattern.py 
# Упрощенная реализация Screenplay Pattern на Python
class Actor:
    def __init__(self, name: str):
        self.name = name

    def attempts_to(self, task):
        task.perform_as(self)

class LoginTask:
    def __init__(self, username, password):
        self.username = username
        self.password = password

    def perform_as(self, actor):
        # Исполнение конкретной атомарной задачи
        print(f"Актер {actor.name} выполняет вход как {self.username}")

# Наглядный тест в стиле Screenplay:
alex = Actor("Алекс (Администратор)")
alex.attempts_to(LoginTask("admin@qa.com", "P@ssword123"))

Итоговые рекомендации архитектора QA

1. Не пытайтесь внедрить все 10 паттернов одновременно в первый же день.
2. Начните с связки Page Object + Page Element для UI и Test Data Builder для тестовых данных.
3. Используйте Facade при росте интеграций между сервисами и Fluent Interface для улучшения читаемости.
